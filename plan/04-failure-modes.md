### F1 — the running check cannot work as specified

This is the single most serious finding, and both halves are directly verified.

§Core mechanism states, correctly, that Claude Desktop calls no `requestSingleInstanceLock`
(confirmed: 0 occurrences in `app.asar`, against a control grep that found `mcpServers` 42×,
`electron` 215×, `autoUpdater` 11×). Electron instantiates Chromium's `ProcessSingleton` **only**
from `requestSingleInstanceLock`. Therefore `SingletonLock`, `SingletonSocket` and
`SingletonCookie` are never created.

Confirmed on disk: with Claude Desktop live as **pid 67426** and 8 processes carrying
`--user-data-dir=/Users/namduong/Library/Application Support/Claude`, `find … -name 'Singleton*'`
returns **nothing** in either real profile.

So §Core mechanism's conclusion and §Running detection's mechanism contradict each other: the
absence of the lock is exactly what §Core mechanism relies on for isolation, and exactly what
makes §Running detection impossible.

The working mechanism is present and verified. leveldb holds an exclusive advisory lock on
`<data_dir>/Local Storage/leveldb/LOCK` for the lifetime of the process:

```
lsof "…/Claude/Local Storage/leveldb/LOCK"
COMMAND   PID     USER   FD   TYPE  NAME
Claude  67426 namduong   39u   REG  …/Claude/Local Storage/leveldb/LOCK
```

A non-blocking `flock(LOCK_EX|LOCK_NB)` that **fails** means running; that **succeeds** (release
immediately) means not running. This works for profiles cdm never launched, survives cdm restarts
(F10), and yields the owning pid for termination without command-line scanning (F6). The file
must never be tested for *existence* — it persists after clean exit (F2), verified present in the
non-running `Claude-Work/`.

### F7 — MAX_PATH, with numbers

Measured on this machine, data dir `/Users/namduong/Library/Application Support/Claude`
(**50 chars**), 18,942 entries:

| Payload | Deepest path, relative to data dir |
| --- | --- |
| Pure Chromium (`Code Cache/electron-preload/<64-hex>.cache`) | **98** |
| Claude app, excluding agent mode (`claude-code-sessions/<uuid>/<uuid>/local_<uuid>.json`) | **142** |
| Agent mode (`local-agent-mode-sessions/…`) | **448** |

Deepest **absolute** path found: **499 chars**.

The load-bearing detail is that agent mode writes a Claude-Code-style project directory whose name
is the **flattened absolute path of the session cwd** — which itself lives inside the data dir:

```
…/Claude/local-agent-mode-sessions/<uuid>/<uuid>/local_<uuid>/.claude/projects/
   -Users-namduong-Library-Application-Support-Claude-local-agent-mode-sessions-<uuid>-<uuid>-local-<uuid>-output-nd5hvj/
   <uuid>/subagents/agent-<17hex>.meta.json
```

The flattening is a 1:1 character substitution, so that component's length **equals** the cwd
length it encodes. Verified exactly: component = **207** = datadir(50) + 157.

Therefore path length is quadratic in the data-dir prefix:

```
component_len = datadir_len + 157
deepest_abs   = 2 × datadir_len + 399      (check: 2×50 + 399 = 499 ✓)
```

**Windows projection — UNVERIFIED (no hardware; also unverified whether agent mode ships on
Windows).** Profiles root `%APPDATA%` = `C:\Users\<user>\AppData\Roaming` = 33 chars for an 8-char
username. With `Claude-` + a 32-char slug, `datadir_len` = 33 + 1 + 7 + 32 = **73**.

| Payload | Projected deepest absolute | vs `MAX_PATH` (260) |
| --- | --- | --- |
| Pure Chromium | 73 + 1 + 98 = **172** | 88 to spare |
| Claude, no agent mode | 73 + 1 + 142 = **216** | 44 to spare |
| Agent mode | 2×73 + 399 = **545** | **over by 285** |
| Agent mode, **zero-length** slug | 2×48 + 399 = **495** | **over by 235** |

**Verdict: the 32-char cap is both insufficient and mis-motivated.** It buys 2×32 = 64 characters
against a 285-character overshoot — it cannot close that gap at any value, including zero. And for
the payload it *was* written for (no agent mode), it is unnecessary: the break-even slug length is
**75 chars**, so 32 is roughly twice as strict as needed.

The constraint that actually binds is one the spec never mentions, and it is on **macOS**:
`NAME_MAX` = 255 (verified via `getconf`). Since `component_len = datadir_len + 157`:

```
datadir_len ≤ 98  ⇒  len(username) + len(slug) ≤ 55
```

With a 32-char slug on this machine the component reaches **240 bytes — 15 bytes of headroom**, and
any username longer than **23 characters** overflows to `ENAMETOOLONG`, breaking agent mode inside
that profile only. Corporate `firstname.lastname` accounts routinely exceed 23.

So: keep a cap, but justify it by `NAME_MAX` and make it adaptive
(`slug_max = clamp(55 − len(username), 12, 32)`), and treat Windows long-path opt-in
(`longPathAware` manifest + `LongPathsEnabled`) as the real Windows mitigation.

### F3/F4 — walking the collision-detection path

The defect is that §Slug normalizes but §Collisions compares raw. Step 1 emits NFC. The other side
of the comparison is `readdir`, which on APFS returns **stored bytes**, not normalized ones —
APFS is normalization-insensitive for *lookup* but preserving for *storage*.

Verified end to end:

```
readdir returned: 43 6c 61 75 64 65 2d 43 61 66 65 cc 81   (NFD, != NFC candidate)
cdm collision check  lc(disk) eq lc(candidate) : NO COLLISION (miss)
filesystem mkdir(candidate)                    : File exists
Rust create_dir_all(candidate) would return    : Ok(())  -> cdm PROCEEDS into the existing folder
dirs on disk now: 1
```

The check misses, the filesystem disagrees, and `create_dir_all` — the natural choice — swallows
the disagreement and returns `Ok(())`. cdm then writes `.cdm-profile` into a folder it does not own
and overwrites `claude_desktop_config.json` with an empty server map. If any later step then fails,
§Create's "rolls back the folder" recursively deletes it (F5).

The ASCII form (F4) needs no Unicode at all: it only needs collision detection to consult the
registry instead of the filesystem, which the spec's wording leaves open ("existing folders" is
undefined), combined with §Reconciliation's instruction to ignore marker-less folders "entirely".
`Claude-Work/` and `Claude/` both exist on this machine and neither has a marker.

Note also that the fix must normalize **and** casefold on both sides, in that order, and that the
`-2`/`-3` loop must apply the same normalized comparison — otherwise the loop can hand back a
candidate that also collides.

### Internal contradictions

Genuine self-contradictions, not merely gaps:

1. **§Core mechanism vs §Running detection.** "Claude Desktop sets no Electron single-instance
   lock (verified in the macOS `app.asar`: no `requestSingleInstanceLock` …)" vs "`is_running(data_dir)`
   combines a known-live child pid with the Chromium lock file (`SingletonLock` / `lockfile`)."
   The first statement is the reason the second cannot work. Both halves verified. (F1)

2. **§Architecture vs §Delete / §Quit / §Platform table.** "Platform adapter … the complete surface
   of OS difference, **four functions**" and "Nothing else branches on platform" — but §Delete needs
   Trash vs Recycle Bin, §Quit needs `SIGTERM`/`SIGKILL` vs `WM_CLOSE`/`taskkill`, and the platform
   table lists both as platform rows. The adapter is at least six functions.

3. **§Product surface, internally.** "Profiles are launched **only** from the manager" contradicts
   the preceding paragraph — tray "Lists profiles; clicking one launches it" — and contradicts
   §Debug CLI's `cdm launch <name>`. Three-way.

4. **§Single instance vs §Debug CLI.** "`tauri-plugin-single-instance`. Launching cdm twice focuses
   the existing instance" vs "Ships in the same binary behind a subcommand so the core can be driven
   without the GUI." Either the CLI takes the single-instance lock (and is unusable, since the
   plugin's action is to focus-and-exit) or it does not (and two processes write one registry). (F9)

5. **§Debug CLI vs §Collisions.** `cdm rename <old> <new>`, `cdm launch <name>`, `cdm delete <name>`
   address profiles **by display name**, while §Collisions states "two profiles may share a display
   name … Neither is an error: the registry is keyed by a stable id." The CLI's addressing scheme is
   ambiguous by construction, and `cdm delete` is destructive.

6. **§Rename step 3 vs the paragraph below it.** "`fs::rename` the folder — same volume, atomic"
   (unconditional) vs "On Windows the move fails outright while Claude holds files open." Step 3 is
   asserted to be an atomic certainty two lines above the statement that it can fail.

7. **§Non-goals vs §Collisions / §Create.** "The unmanaged `Claude/` folder is never read, copied,
   or modified" vs a correct collision check, which *must* read the directory listing including
   `Claude/`, and vs §Create's `mkdir`, which can land on it (F4). The non-goal needs narrowing to
   "never read the *contents* of, copy, or modify" — enumeration is required for correctness.

8. **§Marker file and reconciliation vs §Registry.** Reconciliation scans "`Claude-*` folders",
   but adoption of hand-made folders is offered for folders of any name, and §Registry's `dir` is any
   "current folder". An adopted folder not matching `Claude-*` is invisible to every later
   reconciliation pass. (F18)

9. **§Marker file and reconciliation, internally.** "scan `Claude-*` folders for a `.cdm-profile`
   with that `id`; if found, repair" presumes uniqueness, while the immediately following rule
   ("Folder with a `.cdm-profile` id absent from the registry → re-adopt it") is exactly the rule
   that mints duplicates when a user copies a folder. The two rules together create the ambiguity
   neither resolves. (F8)

### Required changes to existing spec text

**1. §Running detection — replace the mechanism (F1, F2, F10).**

Current:
> `is_running(data_dir)` combines a known-live child pid with the Chromium lock file
> (`SingletonLock` / `lockfile`). Required internally by rename, delete, and quit.

Replacement:
> `is_running(data_dir)` probes the leveldb lock that Claude holds for its whole lifetime:
> a non-blocking exclusive `flock` on `<data_dir>/Local Storage/leveldb/LOCK`. Acquisition
> **fails** ⇒ running; **succeeds** (release immediately) ⇒ not running. The probe also yields
> the owning pid, which Quit uses directly.
>
> Chromium's `SingletonLock` is **not** available: Claude Desktop never calls
> `requestSingleInstanceLock`, so `ProcessSingleton` never runs and the file is never created
> (verified — a live profile with 8 processes has no `Singleton*` entry). Equally, the `LOCK`
> file's **existence** means nothing: leveldb never unlinks it, and it is present in profiles
> that have been shut down cleanly. Only held-ness is meaningful.
>
> Running state is re-derived on every query and never cached across cdm restarts. Pids are
> never persisted. The manager offers a **Force** override for the running check, so a profile
> that is wrongly reported as running can still be renamed or deleted.

**2. §Platform table — replace the lock row (F1).**

Current:
> | Chromium lock | `SingletonLock` (symlink) | `lockfile` |

Replacement:
> | Liveness lock | `Local Storage/leveldb/LOCK`, `flock`-held | `Local Storage\leveldb\LOCK`, `LockFileEx`-held (**UNVERIFIED**) |

**3. §Architecture — correct the adapter's size (contradiction 2).**

Current:
> **Platform adapter** (Rust) — the complete surface of OS difference, four functions:

Replacement:
> **Platform adapter** (Rust) — the complete surface of OS difference, six functions:

and add to that table:

> | `trash(path)` | move to Trash / Recycle Bin; `Err` if unavailable |
> | `terminate(pid, escalate)` | `SIGTERM`→`SIGKILL` / `WM_CLOSE`→`taskkill /F` |

**4. §Collisions — replace the whole paragraph (F3, F4, F15).**

Current:
> Compare the candidate folder **case-insensitively** against existing folders — APFS and NTFS
> are both case-insensitive by default, so `Work` and `work` collide. On collision, append `-2`,
> `-3`, … until free.

Replacement:
> Collision detection enumerates the **filesystem**, not the registry: every directory entry in
> the profiles root, including marker-less and hand-made folders and the unmanaged `Claude/`
> itself. A folder cdm has no entry for is still a folder cdm must not occupy.
>
> Compare on a **normalized key**: `NFC(entry).to_lowercase()`. Both steps are required.
> APFS and NTFS are case-insensitive, so `Work` and `work` collide. APFS is additionally
> normalization-insensitive but byte-preserving, so `readdir` can return NFD bytes for a folder
> the filesystem considers equal to cdm's NFC candidate; a raw comparison misses the collision
> while `mkdir` fails with `EEXIST`.
>
> On collision, append `-2`, `-3`, … until free, comparing each candidate by the same normalized
> key. When resolving a **rename**, the profile's own current folder is excluded from the
> comparison, so a case-only or normalization-only change never collides with itself.

**5. §Create — replace steps 2–5 and the rollback sentence (F3, F5, F16).**

Current:
> 2. `mkdir` the folder.
> 3. Write `.cdm-profile`.
> 4. Write `claude_desktop_config.json` containing `{ "mcpServers": {} }`.
> 5. Append to the registry.

Replacement:
> 2. `create_dir` the folder — **non-recursive**. `EEXIST` is a hard error, never a success:
>    `create_dir_all` would return `Ok(())` on a pre-existing folder and cdm would silently
>    occupy someone else's data.
> 3. Write `claude_desktop_config.json` containing `{ "mcpServers": {} }`.
> 4. Write `.cdm-profile` **last** — the marker is what makes the folder cdm's, so it is written
>    only once the folder is complete.
> 5. Append to the registry.

Current:
> Failure at any step rolls back the folder.

Replacement:
> Failure after step 2 removes the folder — but **only** if step 2 itself created it. Rollback is
> gated on that flag and never recurses into a directory cdm did not create in this operation.
> If rollback itself fails, a complete folder may be left unregistered; startup reconciliation
> re-adopts it with a stem-derived name.

**6. §Rename — steps 1 and 3 (F15, F12, contradiction 6).**

Current:
> 1. Compute the new slug. If it equals the current folder, update the registry only and stop.

Replacement:
> 1. Compute the new slug. Compare to the current folder by normalized key
>    (`NFC(x).to_lowercase()`). If equal, update the registry only and stop — a name change that
>    differs only in case or Unicode normalization must not be routed through collision
>    resolution, which would otherwise hand back `-2`.

Current:
> 3. `fs::rename` the folder — same volume, atomic.

Replacement:
> 3. `fs::rename` the folder. Both paths are inside the fixed profiles root, so this is normally
>    a same-volume, atomic rename. Do **not** add a copy-and-delete fallback: a non-atomic move
>    can leave two folders carrying the same id, which reconciliation cannot resolve. Surface
>    `CrossesDevices`, `EACCES` and `EBUSY` as errors and abort. On network home directories the
>    rename may fail or may not be atomic; the marker file is what makes that recoverable.

**7. §Naming — replace the 32-character rationale (F7).**

Current:
> The 32-character cap exists for Windows. Chromium creates deep paths inside a user-data-dir,
> and a long profile folder eats into `MAX_PATH` for every one of them.

Replacement:
> The cap exists for macOS `NAME_MAX`, not for Windows `MAX_PATH`. Claude's agent mode writes a
> directory whose **name** is the flattened absolute path of a session cwd that lives inside the
> data dir, so a component's length equals `len(data_dir) + 157`. Measured on a real profile:
> 207 bytes against a 255-byte `NAME_MAX`. A 32-character slug reaches 240 — 15 bytes of headroom
> — and overflows for usernames longer than 23 characters. The cap is therefore adaptive:
> `slug_max = clamp(55 − len(username), 12, 32)`.
>
> The cap does **not** solve Windows. Deepest absolute path measured on macOS is 499 characters,
> and length grows as `2 × len(data_dir) + 399`; the Windows projection is ~545 against a
> `MAX_PATH` of 260 — over by 285 even with a zero-length slug (**UNVERIFIED**; also unverified
> whether agent mode ships on Windows). The Windows build must therefore ship long-path support
> (`longPathAware` manifest plus `LongPathsEnabled`) and must not rely on the slug cap.

**8. §Marker file and reconciliation — first two bullets (F8, F18).**

Current:
> - Entry whose `dir` is missing → scan `Claude-*` folders for a `.cdm-profile` with that `id`;
>   if found, repair `dir` (this is how a crash mid-rename heals). If not found, mark the entry
>   **orphaned** and surface it in the manager window rather than deleting it silently.
> - Folder with a `.cdm-profile` id absent from the registry → re-adopt it, deriving the display
>   name from the folder stem.

Replacement:
> - Entry whose `dir` is missing → scan **every** directory entry in the profiles root (not only
>   `Claude-*`, since adopted and Finder-renamed folders need not match) for a `.cdm-profile`
>   with that `id`, collecting **all** matches. Exactly one → repair `dir` (this is how a crash
>   mid-rename heals). None → mark the entry **orphaned**. More than one (the user duplicated a
>   profile folder) → mark the entry **conflicted**, repair nothing, and surface every candidate
>   path in the manager for the user to choose. Never pick by directory order; it is not stable.
> - Folder with a `.cdm-profile` id absent from the registry → re-adopt it, deriving the display
>   name from the folder stem. If that id is already claimed by another folder, mint a **new** id
>   and rewrite the marker, so duplication produces two distinct profiles rather than a conflict.

**9. §Registry — add validation and locking (F9, F13).**

Current:
> Writes are atomic: serialize to a temp file in the same directory, `fsync`, then `rename` over
> the target.

Replacement:
> Writes are atomic: serialize to a temp file in the same directory, `fsync`, then `rename` over
> the target. Atomicity of a single write does not prevent a lost update, so the whole
> **read-modify-write** is performed under an advisory exclusive lock on
> `<manager data>/registry.json.lock` (`flock` / `LockFileEx`), re-reading the file after
> acquiring it. This is required because the debug CLI ships in the same binary and can run while
> the GUI holds the registry in memory; `tauri-plugin-single-instance` does not cover it, as a
> CLI subcommand exits before the Tauri builder runs.
>
> On load, every `dir` is validated as a single path component matching
> `^Claude-[A-Za-z0-9._-]+$` — not absolute, no separators, no `..`. An entry failing validation
> is surfaced and never acted on: `dir` reaches both `--user-data-dir` and the Delete path, and
> `registry.json` is a plain file the user can edit.

**10. §Quit — replace the fallback (F6).**

Current:
> Terminate by pid when cdm launched the profile this session. When it did not (cdm was
> restarted), locate the process by scanning for one whose command line contains the profile's
> `--user-data-dir`.

Replacement:
> Terminate by the pid holding the profile's liveness lock (see Running detection), which works
> whether or not cdm launched it. If a command-line scan is used as a secondary check, match the
> flag's value **exactly** on an argv boundary — never substring containment. `…/Claude-Work` is
> a substring of `…/Claude-Work-2`, and the `-2` suffix is generated by cdm's own collision rule,
> so a containment test would quit the wrong profile. Terminate the main process and let its
> children exit; a single data dir has ~8–29 processes carrying the flag, all of which match.

**11. §Product surface — resolve the launch-surface contradiction (contradiction 3).**

Current:
> Profiles are launched **only** from the manager. No `.app` bundles or `.lnk` shortcuts are
> generated, so there is nothing on disk to keep in sync with a rename.

Replacement:
> Profiles are launched only from cdm itself — the tray, the manager window, or the debug CLI.
> No `.app` bundles or `.lnk` shortcuts are generated, so there is nothing on disk to keep in
> sync with a rename.

**12. §Non-goals — narrow the "never read" claim (contradiction 7).**

Current:
> - **No import of the existing install.** The unmanaged `Claude/` folder is never read, copied,
>   or modified.

Replacement:
> - **No import of the existing install.** The unmanaged `Claude/` folder's *contents* are never
>   read, copied, or modified. Its **name** is enumerated, because collision detection must know
>   it exists in order to never occupy it.

**13. §Debug CLI — disambiguate addressing (contradiction 5).**

Add below the command table:

> Commands take a display name, which §Collisions permits to be duplicated. When a name matches
> more than one profile the command **fails** and lists the matching ids; `--id` addresses a
> profile unambiguously. Destructive commands never guess.

**14. §Core mechanism — pin the spawn invariant (F14).**

Add after the `launch(profile)` snippet:

> Spawn always passes an argv **array**; the data dir is one element and is never interpolated
> into a shell string. Combined with the slug algorithm — which maps every character outside
> `[A-Za-z0-9._-]` and space to `-`, so separators, drive colons and NUL cannot survive, and
> which is prefixed with `Claude-` so the result can never begin with `-` — no user-typed name
> can escape the profiles root, produce an absolute path, or inject an argument. This was traced
> against the algorithm as written, including the `-2` collision-suffix path, and no escape was
> found. The invariant is asserted at the boundary: the slug's output must be a single path
> component.
